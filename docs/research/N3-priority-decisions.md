## 1. 總優先序表

**判定邏輯(效益/成本矩陣)**:「收益對北極星」= 對 M0 定義的單一專案一條龍(腳本→分鏡→逐幕→拼接→輸出→打包)+ 信任/可靠性止血的貢獻;「成本/風險」= 工程量級+破壞性風險。四象限:

- **先做** = 高收益 × 低成本(立即做,槓桿最大)
- **次做** = 高收益 × 高成本(排進本月/下月,需拆解)
- **緩做** = 低收益 × 低成本(有餘力再做,不擋路)
- **不做** = 低收益 × 高成本(現階段不值得,除非情勢改變)

## 2. 這週只能做 3 件事

### 【本週-1】修 CI runner(AIDV-958)

- **為什麼**:所有合併目前都在裸奔——PR Gate 100% 在 2-16 秒內 failure,是帳務/額度問題,不是程式碼問題。00-summary §3 明白寫「不做後面全部低效」;F §4.1 也把它列為收斂 PR 前的最優先流程債。
- **解鎖什麼**:恢復自動把關,讓後面所有 PR 合併(包含 #1298、aidv-autodev/aidv-longloop 的自動合併)不必只靠本機 gate 裸眼判斷;也讓「本週-3」的 PR 大掃除有真正的安全網。
- **誰能做**:**Bruce**(GitHub Billing/spending limit 頁面確認額度問題,這是帳號層權限,工程side 進不去)+ 完成後由智能助手把 eval/e2e 排進 CI(工程可做)。

### 【本週-2】修 G3 178-tool gate(=R10)+ 順手修 R1 雙重退款

- **為什麼**:M0 藍圖明言這是「唯一硬前置」——精靈工具 178 個 case 目前規劃會過、執行必敗,是光球核心賣點名存實亡的根因,也是分鏡管線執行化(M0 Phase 1)和 AI 動手引導的共同依賴。R1 雙重退款是可穩定重現的套利漏洞,M0 建議同一批順手修,成本近零。
- **解鎖什麼**:解鎖 M0 Phase 1 全部後續工作(分鏡管線執行化、AI 讀專案上下文動手做),避免把後續體驗建立在「假成功」之上;同時止血一個可套利的資安漏洞。
- **誰能做**:**需工程**(修 `agentToolExecutor.ts` gate 區塊 + `global-agent-tools.ts` 補 registry + 「不 mock 執行器」的整合測試)。此項是 aidv-autodev 的理想候選——範圍明確、非破壞性、flag 可控,可自動跑完整條 pipeline 到合併(見 §4)。

### 【本週-3】PR/Jira 大掃除第一刀:合 #1298 + 關 4 個已覆蓋 PR + Jira「進行中」41 張大掃除

- **為什麼**:F §3 揭露的系統性落差(列車合了卡沒關、Done≠上線、bot 重複開 PR)全部源自「看板不是真相」。41 張「進行中」全掛同一帳號,WIP=1 名存實亡,每次挑下一張卡都要人工重新核對現況——這是後面所有排序決策(包含 aidv-plan/aidv-board 自動取卡)能不能準的基礎。
- **解鎖什麼**:恢復 Jira 看板與 GitHub PR 列表的真實性,讓 aidv-plan/aidv-board/aidv-longloop 之後「取下一張卡」不會挑到已經做完或已過時的卡;也讓 #1298 對應的四張進行中卡真正收尾。
- **誰能做**:**Bruce 小白可做大部分**(Jira 狀態轉換、確認哪些卡要留「進行中」)+ **智能助手主導執行**(aidv-board/aidv-plan 跑批次操作、#1298 合併前的 fetch+rebase+Docker migration 驗證需工程把關)。批次關閉 71 個殭屍 PR 中「高確定性」子集(見 §5 決策卡)可以這週先動,其餘留到本月稍後。

## 5. 決策卡:PR/卡大掃除

**要決定什麼**:是否一次性(本週內)批次關閉 71 個殭屍 PR(behind >300 commits)+ 15 個 open issue,以及對 41 張「進行中」Jira 卡做狀態大掃除。

**依據**:
- F §2.1/2.4:89 個 open PR 中 71 個(behind>300,2026-04~05 建立)已被 main 後續演進覆蓋——railway bot 系列 13 個、codex 系列 ~24 個(含多組同題雙開)、claude 系列(光球/精靈時代功能,架構已翻代)、docs 快照 10 個、migration 修復 3 個、#98(對已無意義 PR 的解衝突 PR)。
- F §2.6:15 個 open issue 中 11 個 `[AI]` 自動提案已被 AIDV-224(XSS 收斂)/AIDV-251(CSP)大幅覆蓋,4 個手寫 issue 目標物已在 main、任務體系已整體遷至 Jira AIDV。
- F §1.3:41 張「進行中」卡全掛同一帳號(bots 共用),WIP=1 名存實亡。
- 00-summary §3:「第 0 步(流程地基,不做後面全部低效)」把 PR/issue/Jira 收斂列為最優先。

**選項**:
- **A. 一次性全批關閉**(71 個 PR + 15 個 issue 同一天處理完):效率最高,但風險是 71 個裡少數殭屍 PR 可能藏著仍有參考價值的小修改(尤其 codex 系列的雙開組,可能有一組想法比另一組好但都沒被抄進 main),一次關掉等於永久放棄,且若日後想找回需要翻 GitHub 關閉紀錄。
- **B. 分兩批+人工抽查**:第一批這週先關「高確定性」子集——railway bot 13 個(2026-04~05 hotfix,問題已用其他方式修畢)+ 已證實被具體 PR 取代的 4 個(#1268/#1250/#1038/#1255)+ docs 快照 10 個(內容已被 docs/research 取代)+ 15 個 issue 全部(交叉驗證證據最扎實),共約 27 個 PR + 15 個 issue。第二批(codex 系列 ~24 個 + claude 系列 + 過期邊緣)留到下一輪,由人工快速掃過標題+diff 摘要後再關,避免自動化誤關到「還沒被抄進 main 但仍值得抄」的分支。
- **C. 維持現狀不動**:零風險,但 89 個 open PR 的噪音持續誤導後續代理誤判「還有人在做」,也讓每次 `git merge-tree` 掃描的成本線性增加。

**建議**:選 **B**。理由:15 個 issue 與 railway bot/docs 快照/已覆蓋 PR 這批的證據最扎實(F 文件逐一列出對應覆蓋者),關閉零損失;codex 系列因為有「同題雙開」情況,值得花一輪人工核對確認沒有遺漏可用想法,再批次關閉。「進行中」41 張卡:bot 產的([QA 探查]/[資安巡檢]/[opt] 類)可批量轉回 Backlog;涉及人(合併列車四卡、AIDV-859 等在飛卡)保留「進行中」。

**需要 Bruce 拍板的點**:
1. 是否同意「關閉 = 放棄再翻找」這個決斷——尤其 codex 系列可能藏著沒被抄進 main 但仍有價值的實作細節,一旦關閉且分支被清理就難以找回(建議至少先留一份「已關閉清單」存檔於 `docs/research`,再放行關閉)。
2. 這類批次操作是否可授權智能助手/aidv-board **自動執行**,還是要 Bruce 先過一遍清單(哪怕只看標題)再按確認——這決定了本週能不能真的把 F-8 排進「本週 3 件事」的候選。
3. #1065(FreeLLMAPI 免費層)不在這次批次關閉範圍內,需要 Bruce 先回答「還要不要免費層」(見 §4.3),再決定是 rebase 保留還是併入這輪關閉。
4. GitHub 端可見性/審計考量:大量關閉 PR/issue 是否需要在關閉留言統一附上「已被 main 演進覆蓋,對應工作見 Jira AIDV」字樣(F §4.1 已建議此留言格式),讓外部協作者不會誤以為專案棄置——建議照此格式執行,無需額外決策。
