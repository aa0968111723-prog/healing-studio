# X6 — learnHub.ts router 逐行深挖(地毯掃描 wave X)
- 產生日期:2026-07-03
- 依據 commit:812f6fdb
- 稽核檔案:server/routers/learnHub.ts(1103 行)

## 檔案角色(先讀後判)

`server/routers/learnHub.ts` 是「學習文件中心」的 tRPC router,管理三種內容型別:

1. **docs**(學習文件):唯一有 DB 表(`learnModules` / `learn_modules`,見 `drizzle/schema.ts:4481-4506`)落地的型別。啟動時由 `initLearnHubFromDb()`(37-138 行)從 DB 灌回記憶體陣列 `docs`(50 行),`create`/`update`/`delete`/`importDocs` 會同時寫記憶體 + 嘗試寫 DB。
2. **videos**(影片)與 **quizzes**(測驗):只活在模組級記憶體陣列(145、153 行),完全沒有對應 DB 表,CRUD 全部只動記憶體 —— 這是已知、有註解、有專屬回歸測試鎖定的限制(AIDV-190,838、981 行的 `ephemeral: true`,對照 `server/routers/learnHub.ephemeral.test.ts`),**非本次新發現**。
3. 另外還內建 3 篇「自動彙整文件」(`buildModelCoverageDoc` / `buildQuizCoverageDoc` / `buildAutomationMaintenanceDoc`,218-475 行),於模組載入時透過 `syncAutoGeneratedLearnDocs()`(477 行)產生一次,之後不再重跑。

本檔同時是**光球(Orb)系統提示詞**與**「學學」學習專員 spirit agent**的資料源頭:`getAllLearnDocsForOrbIndex()`(74-92 行)、`__getAllVideos()`(161-183 行)、`__getAllQuizzes()`(185-207 行)分別被 `server/services/siteKnowledge.ts` 與 `server/services/spiritTools/learningSpecialistTools.ts` 匯入使用 —— 這條路徑是本次「內容注入進 LLM/RAG」與「W6 快取失效寫入端」兩個追查重點的關鍵交會點。

以下依「發現 → 影響 → 建議」、按嚴重度排序。每則發現皆已對照實際程式碼逐行核實。

## 🔴 高:`importDocs` 略過 `create`/`update` 都有的清洗步驟,未清洗文字直達光球系統提示詞與「學學」工具輸出(cluster: injection)

**發現**

- `create`(adminProcedure)在寫入前明確清洗三個文字欄位:
  ```ts
  // learnHub.ts:589-591
  title: sanitizePlainText(input.title),
  summary: sanitizePlainText(input.summary),
  content: sanitizeRichText(input.content),
  ```
  `update` 也對應做了同樣的條件式清洗(`learnHub.ts:666-668`)。
- 但 `importDocs`(716-791 行,批量匯入,同樣是 `adminProcedure`)完全沒有呼叫 `sanitizePlainText` / `sanitizeRichText`:
  ```ts
  // learnHub.ts:753-761
  .mutation(async ({ input }) => {
    const now = new Date();
    const nowIso = now.toISOString();
    const imported: LearnDoc[] = input.docs.map((item, idx) => ({
      id: `import-${now.getTime()}-${idx}`,
      ...item,               // title / summary / content 原樣沿用,零清洗
      publishedAt: nowIso,
      updatedAt: nowIso,
    }));
  ```
  之後 `docs = [...imported, ...docs]`(789 行)把這些未清洗物件直接併入全站唯一的記憶體陣列,與 `create` 寫入的、已清洗的文件混在同一份清單裡,下游完全無法分辨。
- `server/utils/sanitize.ts:1-19` 的函式註解明講這是設計上的唯一清洗邊界:「Applied at the server boundary so the sanitized value is what gets persisted」——`importDocs` 打破了這個不變量。
- 追蹤下游:`getAllLearnDocsForOrbIndex()`(learnHub.ts:74-92)把 `docs` 逐筆投影出 `summary`,不分是否來自 `importDocs`;`server/services/siteKnowledge.ts:139-140` 的 `buildLearnHubIndexKnowledge()` 把 `d.summary` **原樣字串拼接**進光球系統提示詞的「學習文件中心索引(光球可直接引用)」區塊,且緊鄰教光球辨識 `[ACTION:navigate:...]` 動作語法的指示行(同檔 163-166 行)。`server/services/spiritTools/learningSpecialistTools.ts` 的「學學」spirit 工具也直接消費同一批 `summary`/`title` 做為 LLM 工具回傳內容(見下一則發現的呼叫鏈)。
- 對照:本檔的 `learnHub.seed.test.ts` / `learnHub.ephemeral.test.ts` 均未涵蓋 `importDocs` 的清洗行為,此落差目前無回歸測試守著。

**影響**

- 只要 admin(或任何取得 admin 權限的呼叫者)用 `importDocs` 匯入內容,`title`/`summary`/`content` 可以帶有未經過濾的字串 —— 包含偽裝成系統/動作指令的文字(例如偽造 `[ACTION:...]`、`[CONFIRM:true]` 或角色標記字串) —— 這些字串會被原樣放進光球系統提示詞裡「請優先引用」的信任區塊,以及「學學」工具對使用者的回覆素材,構成比一般聊天訊息注入更高信任層級的旁路。
- 前端 `LearnHub.tsx` 的 `renderMarkdown()`(`client/src/pages/LearnHub.tsx:165-232`)在轉換前會先 `escapeHtml()`,目前**沒有**因此在該頁面造成可執行的 stored XSS(見下方「已驗證排除」);但伺服器端的清洗邊界被繞過,任何未來新增的內容消費端(匯出、SSR、其他 admin 檢視畫面、RAG pipeline)若沒有各自重新做等效逃逸,就會直接暴露。

**建議**

- 在 `importDocs` 的 `.map()` 內對每筆 `item` 補上與 `create` 完全相同的 `sanitizePlainText`/`sanitizeRichText` 呼叫,消除與單筆 `create` 的行為落差。
- 補一條測試:匯入含 `<script>`/`[ACTION:...]` 樣式字串的 payload,斷言存進 `docs` 陣列與 DB 的值已被清洗,鎖住這條路徑不再退化。

## 🟠 高:寫入端(create/update/delete/importDocs)從未讓下游至少兩個獨立記憶體快取失效 —— 確認並擴大 W6 的 `learnHubOrbIndexCache` 發現(cluster: persistence)

**發現**

- W6(`docs/research/W6-siteknowledge-deepdive.md`)已從讀取端指出:`server/services/siteKnowledge.ts:81-116` 的 `learnHubOrbIndexCache` 是一個「以為 `docs` 靜態不變」的 `Map`,只有測試用的 `__resetLearnHubOrbIndexCacheForTests()`,生產路徑永不清除。
- 本次從**寫入端**(learnHub.ts)逐一核實:`create`(620 行 `docs.unshift(newDoc)`)、`update`(663-670 行 `docs[idx] = {...}`)、`delete`(701 行 `docs.splice(idx, 1)`)、`importDocs`(789 行 `docs = [...imported, ...docs]`)四條會改變 `docs` 內容的路徑,**沒有任何一條**呼叫 `learnHubOrbIndexCache` 相關的清除函式,也沒有匯入 `siteKnowledge.ts` 的任何符號(檔內對 `siteKnowledge` 唯一的兩處出現只是註解,見 67、72、156 行)。
- 更進一步,本次額外核實出**第二個**、W6 未提及的獨立受害快取:`server/services/spiritTools/learningSpecialistTools.ts:74`(`let cachedLearnHub: LearnHubModule | null = null;`)。其 `loadLearnHubSync()`(90-118 行)第一次成功呼叫 `getAllLearnDocsForOrbIndex()`/`__getAllVideos()`/`__getAllQuizzes()` 後就把結果存進 `cachedLearnHub` 且永久沿用;生產路徑同樣沒有任何清除呼叫,唯一的重置入口 `__setLearnHubForTest()`(135-138 行)連測試檔都不存在(`find` 未找到 `learningSpecialistTools.test.ts`),等於這條快取的過期行為完全沒有回歸測試覆蓋。
- 佐證測試本身也把錯誤前提寫進斷言:`server/orb-learn-hub-memoization.test.ts:1-9` 的檔頭註解直接複述「The underlying `docs` array in `learnHub.ts` is module-load static」,而本檔案 50 行的宣告其實是 `let docs: LearnDoc[] = [...SEED_DOCS]`(可變),209-216 行的 `upsertSeedDoc` 與上述四個 mutation 都會改它 —— 前提已被證偽,但測試只鎖住「同一次呼叫回傳同一參照」的記憶化行為,並未驗證「寫入後快取是否失效」。

**影響**

- 任一管理員透過 `update`/`delete` 修改精選狀態、分類、標題摘要,或下架一篇文件後,光球系統提示詞(`buildLearnHubIndexKnowledge`)與站內即時搜尋(`orbUnifiedSearch.ts:368`)都會繼續使用舊資料,直到整個 process 重啟。
- 「學學」學習專員 spirit 的工具(`getNextLearningStep`、`recommendForContext` 等,`learningSpecialistTools.ts:1151`、`1229` 呼叫 `ensureLearnHubLoaded()`)同樣會對使用者持續推薦已刪除或已改版的文件/影片/測驗 deep link,兩條路徑互相獨立、需要各自修。
- 實務後果:管理員下架的文件,AI 助手仍可能用 `[ACTION:navigate:/learn?docId=<id>]` 帶使用者點進已刪除的頁面(前端 `getById` 會回 404,見 536-538 行),造成「AI 推薦死連結」的使用者體驗問題。

**建議**

- 依 W6 建議,在 `learnHub.ts` 的 `docs` 每次被寫入(`create`/`update`/`delete`/`importDocs`/`upsertSeedDoc`)時遞增一個 module-level `docsVersion`,兩個下游快取(`siteKnowledge.ts` 的 `learnHubOrbIndexCache`、`learningSpecialistTools.ts` 的 `cachedLearnHub`)改用 `${limit}:${docsVersion}` 或直接在版本變動時清空,或乾脆把 `__resetLearnHubOrbIndexCacheForTests()` 改名並在這四個 mutation 尾端呼叫。
- 由於現在確認有 2 個獨立快取,建議抽出共用的「learnHub 內容已變更」訂閱/廣播點,而非各自修各自的快取,避免未來第三個消費端重蹈覆轍。

## 🟠 高:admin mutation 對 DB 寫入失敗一律吞掉錯誤,記憶體仍視為成功 —— 造成「刪除後復活」「新增後消失」(cluster: persistence)

**發現**

- 四個對 `learnModules` 表做 DB 操作的 mutation,DB 呼叫全部包在 `try { await db.xxx(...) } catch (dbErr) { console.warn(...) }` 裡,錯誤只印 log,從不 rethrow、不回傳給呼叫端、不回滾已經做的記憶體變更:
  - `create`:614-617 行 catch 後,620 行仍執行 `docs.unshift(newDoc)`,回傳的 `newDoc` 讓前端以為已永久保存。
  - `update`:686-688 行 catch,691 行仍 `return docs[idx]`(已修改)。
  - `delete`:698-701 行**先**做 `docs.splice(idx, 1)`,703-709 行才嘗試 DB delete 並在失敗時只 warn,712 行仍 `return { success: true }`。
  - `importDocs`:784-786 行 catch,789 行仍把 `imported` 併入 `docs` 並回傳 `{ success: true, count }`。
- 三種具體資料完整性後果(以單一 process、DB 暫時性錯誤即可觸發,不需要多副本部署):
  1. **create 之後消失**:若 DB insert 失敗(例如逾時、連線抖動),`newDoc` 只存在於當前 process 記憶體;下次重啟時 `initLearnHubFromDb()`(99-138 行)只從 DB 灌回,該文件永久消失,但 admin 當下收到的是成功回應。
  2. **delete 之後復活**:若 DB delete 失敗,`docs.splice` 已讓文件從當前畫面消失,`return { success: true }` 讓 admin 以為刪除成功;但 DB 裡的列還在,下次重啟 `initLearnHubFromDb()` 會把它重新灌回記憶體,文件「復活」。
  3. **update 被靜默還原**:若 DB update 失敗,當前 process 看得到新內容,但重啟後又回到 DB 裡的舊值,等於編輯被悄悄撤銷。
- Railway 部署設定(`railway.toml`:`restartPolicyType = "ON_FAILURE"` + 每次 deploy)代表這類「重啟」並非罕見邊角案例,而是每次上版都會經過的正常流程。

**影響**

- 管理員完全無法從 API 回應判斷「這次操作是否真的落地到 DB」,現有回傳值(`newDoc`/`docs[idx]`/`{ success: true }`)在 DB 失敗時仍與成功時一模一樣,是虛假的持久化保證。
- 三種後果都要等到下次重啟才會現形,難以在當下的 QA / 手動測試中發現,屬於「看起來正常,實際上資料會漂移」的隱性缺陷。

**建議**

- DB 寫入失敗時至少要:(a) 用 `logger.error`/`captureError` 取代 `console.warn`,讓維運能觀測到;(b) 讓回應攜帶一個「僅暫存於本機、尚未持久化」的旗標(仿照 videoList/quizList 既有的 `ephemeral: true` 模式),而不是靜默假裝成功。
- 若要求強一致性,DB 寫入失敗時應該回滾對應的記憶體變更(`create`/`importDocs` 移除剛 push 的項目;`delete` 復原 `docs.splice` 移除的項目),並對呼叫端拋出可辨識的錯誤,而不是回傳「成功」。

## 🟡 中:文件/影片/測驗 ID 皆用毫秒級 `Date.now()` 產生,無碰撞防護(cluster: persistence)

**發現**

- 四處 ID 產生方式:
  - `create`:`learnHub.ts:587` `id: \`custom-${now.getTime()}\``
  - `importDocs`:`learnHub.ts:757` `id: \`import-${now.getTime()}-${idx}\``(批次內用 `idx` 保證不撞,但跨兩次呼叫仍可能撞)
  - `videoCreate`:`learnHub.ts:879` `id: \`video-${Date.now()}\``
  - `quizCreate`:`learnHub.ts:1033` `id: \`quiz-${Date.now()}\``
- `docs`/`videos`/`quizzes` 都是普通陣列,沒有唯一性檢查;`getById`/`update`/`delete` 一律用 `.find()`/`.findIndex()` 找「第一筆符合 id 的項目」(例如 535、658、698、846、913、929、989、1081、1097 行)。

**影響**

- 兩次在同一毫秒內送出的 `create`/`videoCreate`/`quizCreate`(常見於使用者連點兩下送出按鈕,或自動化腳本快速連續呼叫)會產生完全相同的 `id`。之後陣列裡出現兩筆同 id 項目,`update`/`delete` 只會動到 `findIndex` 找到的第一筆,另一筆會變成無法被一般 CRUD 觸及的「孤兒重複項」;`create` 情境下還會讓 DB insert 因為主鍵重複而失敗(觸發上一則發現的吞錯誤路徑)。

**建議**

- 改用具唯一性保證的 ID 產生方式(如 `crypto.randomUUID()` 或既有的 nanoid 工具),或至少在 `getTime()` 後綴加一段隨機字串,徹底消除毫秒級碰撞的可能性。

## 已驗證排除的疑慮(negative results)

- **admin mutation 授權**:本檔 10 個會修改狀態的 mutation(`create:551`、`update:625`、`delete:695`、`importDocs:716`、`videoCreate:853`、`videoUpdate:889`、`videoDelete:926`、`quizCreate:996`、`quizUpdate:1043`、`quizDelete:1094`)全部正確掛載 `adminProcedure`,無一遺漏成 `publicProcedure`/`protectedProcedure`。追查 `adminProcedure` 實作(`server/_core/trpc.ts:69-88`)確認它會呼叫 `isAdmin(ctx.user.role)`,未通過即拋 `FORBIDDEN`——本檔案層級沒有找到授權缺口。(`isAdmin()`/`ctx.user` 賦值機制的正確性屬於其他檔案範圍,未在本檔驗證。)
- **IDOR(跨用戶存取)**:`LearnDoc`/`LearnVideo`/`LearnQuiz` 型別(`server/routers/learnHub.seed.ts`)與對應 DB 表 `learn_modules`(`drizzle/schema.ts:4481-4506`)都沒有 `userId`/`ownerId`/`createdBy` 欄位——這是全站共用的管理員維護內容,不是「使用者自己的資料」,因此本檔不存在「A 使用者讀到 B 使用者資料」意義下的 IDOR 攻擊面。
- **計費/退款**:對 `server/routers/learnHub.ts` 全文檢索 `credit`/`point`/`billing`/`deduct`/`cost` 無任何結果——本檔案本身不含扣點/計費邏輯。(下游 `server/jobs/learnDocSyncer.ts` 的 LLM 合成呼叫是否因本檔的 `addLearnDoc`/`hasLearnDoc` 只寫記憶體、重啟即遺失而重複產生 LLM 成本,屬於另一檔案的呼叫鏈,未在本檔逐行稽核範圍內做完整驗證,僅作為旁證:`addLearnDoc`(56-58 行)確實只 `docs.unshift(doc)`,從未寫 DB。)
- **孤兒頁(R14)**:本檔的三個前端消費者 —— `/learn`(`client/src/pages/LearnHub.tsx`,經 `App.tsx:67,346` 註冊路由並掛在 `DashboardLayout` 導覽下)、`LearnDocsPanel.tsx`、`ContentTab.tsx`(經 `AdminPanel.tsx:22,64` 正確掛進「內容」分頁)—— 均能從既有導覽/路由表到達,未發現無法觸及的孤兒頁面。
- **前端 stored XSS**:即使 `importDocs` 略過伺服器端清洗(見上方高風險發現),`client/src/pages/LearnHub.tsx:165-232` 的 `renderMarkdown()` 會在轉 Markdown 前先對全文做 `escapeHtml()`,目前透過 `/learn` 頁面本身**不會**形成可執行的 stored XSS;風險僅限於伺服器端清洗邊界被繞過本身,以及該內容原樣進入光球系統提示詞(已於上方列為高風險 injection 發現)。
- **video/quiz 無 DB 持久化**:`videoCreate`/`videoUpdate`/`videoDelete`/`quizCreate`/`quizUpdate`/`quizDelete` 完全只動記憶體、重啟即遺失,這是已知、已在程式碼註解(AIDV-190)與專屬測試(`server/routers/learnHub.ephemeral.test.ts`)中被誠實揭露與鎖定的限制,並非本次新發現的缺陷。
