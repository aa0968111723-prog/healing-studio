## 0. 問題重述與判準

Bruce 的問題不是「這系統好不好」,是「如果重新蓋一個網站,這個 repo 值多少」。三個選項要回答同一組問題:

1. 到北極星(ProjectFlowGuide 五步引導,M2)最短路徑是哪條?
2. 相對工時(以「原地修復全量」= 1x 為基準)?
3. second-system / 回歸 / 資料遷移風險各多大?
4. 什麼情境下該選它?
5. 對「prod 已有真實使用者與資料」的敏感度?

驗證用的具體數字(本次於 HEAD 複核,非臆測):
- `agentToolExecutor.ts` 實測 8087 行(matches I 稽核數字)。
- `drizzle/schema.ts` 內 `*Table(` 定義 102 處;最新 migration snapshot(`0008_snapshot.json`)僅 24 個 table object——確認「schema 比 migration 領先 78 張表」的落後幅度(DI-01/SD)。
- schema 內欄位命名確認漂移共存:`userId` 251 處、`user_id` 7 處、`ownerUserId` 4 處、`createdBy` 7 處(DI/SD)。
- `deductUserPoints`/`atomicClaimJobRefund` 被 20 個檔案引用(routers/generate.ts、director.ts、proStudio.ts、services/postGenActions.ts、cost/ledger.ts、orbCostGuard.ts、db.ts 等)——這條原語耦合廣但耦合的都是「呼叫它」而非「侵入它內部」,適合抽成獨立套件(見 §3 階段一)。
- `secretCrypto.ts` 僅 125 行,無框架依賴,是全 repo 少數「零耦合、可直接搬」的模組之一。
- `ProjectFlowGuide.tsx` 僅 204 行,是北極星的 UI 錨點,體積小但目前處於「後段斷裂 + prod 旗標 OFF」狀態(M2/M0 既有結論)。

## 1. 選項 A — 從零 Greenfield

### 到北極星的路徑
新建 schema(FK 齊全)→ 新建 authz 中介層 → 重寫計費 ledger → 重寫生成派工 → 重寫五步引導。等於把 M0 藍圖的「解放既有零件」全部改成「重新發明零件」,多繞一圈。

### 相對工時
**2.5x–3.5x**(對照「原地修復全量」)。多出來的成本主要不是寫新 UI(那部分本來就要碰),而是：
1. 計費原語要重新做「FOR UPDATE 原子 + CAS 回滾」的並發正確性,且要重新踩過 W5 已經踩過的並發回歸測試坑；
2. secretCrypto(AES-256-GCM+scrypt,GC3)這種安全原語重寫一次就多一次被寫錯的機會;
3. fal/replicate/suno 三方整合、模型目錄、RAG 管線全部要重新對接、重新驗證計費行為,這些不是「架構債」,是純工程量,greenfield 不會讓它變快。

### 風險
- **Second-system 風險最高**:團隊會忍不住把「順便」修的東西越修越多,範圍蔓延到北極星之外(五步引導原本就是相對克制的範圍,重寫容易被過度設計)。
- **無回歸風險(對舊系統而言)**,因為沒有舊系統要保護——但這等於把 W5/GC3 已驗證過的正確性「歸零重測」,實質是新增風險而非消除風險。
- **資料遷移風險**:如果 prod 已有使用者,greenfield 必須做「一次性大遷移」,而非漸進遷移——遷移窗口內的雙寫/回滾方案要另外設計,且沒有舊 code 可以參照驗證遷移是否正確。

### 何時該選它
- 需 Bruce 提供:是否要保留現有付費使用者/資料;是否有時程壓力要求某個日期前上線;團隊規模與是否有能力同時維護兩套系統。
- 僅在「prod 使用者數 ≈ 0 或可承受一次性重新引導」且「時程寬鬆到可以重新驗證所有並發/安全正確性」時才該選——否則等於用工時買一個「重新踩雷」的機會,不划算。

### 對 prod 真實使用者/資料的敏感度
**最高**。一次性遷移窗口 + 重新驗證計費正確性,任何疏漏都直接等於資損或帳務糾紛。若 prod 有真實金流使用者,不建議此選項。

## 2. 選項 B — 原地修復(M0 既有立場)

### 到北極星的路徑
沿用 M0 藍圖:解放/接線/補對齊門——五步引導本身已存在(204 行,結構完整),真正缺的是「後段斷裂處修補 + prod 旗標打開」+ 把 IA0 建議的授權中介層、冪等 ledger+outbox、webhook HMAC 補進既有系統。

### 相對工時
**1x(基準)**。這是 M0 既有藍圖已估過的路徑,本研究不重估,只補一個對照維度:它的工時優勢建立在「W5/GC3/contextPackets/falDispatcher/RAG 這些已驗證正確的零件不用重做」上——這正是這批零件的價值所在。

### 風險
- **回歸風險中高**:8087 行 `agentToolExecutor.ts` + 178 個不可達工具、三套並存記帳、shell 路由 shadow,這些「debt」本身就是「改一處驚動多處」的地雷區。原地修復要在不觸發回歸的前提下拆解這坨代碼,難度不小。
- **Second-system 風險低**:範圍被既有藍圖鎖定,不容易蔓延。
- **資料遷移風險低**:不遷移,直接在原 schema 上補 FK、修命名——但要注意:**補 FK 到 102 表其中之一,如果該表已有違反 FK 約束的髒資料(例如孤兒列指向已刪除的 userId),遷移腳本會直接失敗**,這是原地修復路線特有的「隱藏遷移風險」,不是不遷移就沒有遷移風險。
- 系統性債(Y5/CC2 的 IDOR 反模式、B-27/B-31/B-32/B-22/X3 計費外圈失效)若不先建「集中式物件授權中介」+「冪等計費 ledger」這兩個閘門,原地打補丁只會不斷復發(這是既有稽核反覆強調的「補丁打地鼠」結論,不是新論點)。

### 何時該選它
- 需 Bruce 提供:目前 prod 是否已有真實使用者與資料量級,以及團隊是否有能力在原地做「先建閘門、後遷移補丁」這種較高紀律的修復順序(否則會退化成真的打地鼠)。
- **prod 已有真實使用者/資料時的預設選項**——除非既有代碼庫的耦合已經高到「改一處要動十處」讓維護成本超過其保存價值(目前證據不支持這個判斷:核心原語耦合廣但耦合方式健康,見 §0 的 deductUserPoints 調用點分析)。

### 對 prod 真實使用者/資料的敏感度
**低**(相對 A、C 選項而言)——不遷移就沒有遷移窗口風險,但仍要處理「FK 補齊時撞到既有髒資料」的邊界情況。

## 3. 選項 C — 乾淨地基移植 / Strangler(用 repo 當零件庫 + 規格庫)

### 核心思路
不是「修這個系統」,也不是「重寫一個系統」,是「新建一個乾淨地基(FK 齊全的 schema + 集中式授權中介 + 冪等計費 ledger),把已驗證正確的零件(W5 計費原語、GC3 加密、contextPackets、falDispatcher、RAG)整包搬進新地基,同時把已知帶病的殼(agentToolExecutor 巨石、三套並存記帳、shell 路由 shadow)留在舊系統裡逐步汰換」。新舊系統透過 strangler fig 模式並行,流量逐模組切過去。

### 到北極星的路徑
北極星(五步引導)本身是最小、最乾淨的部分(204 行,無巨石依賴),適合作為「第一個切過去的完整垂直切片」而不是「最後才做」——這與 M0 原地修復路線的順序假設不同,值得 Bruce 留意:如果選 C,五步引導可以是 P1 而非 Pn。

### 相對工時
**1.3x–1.6x**(對照原地修復 1x)。比原地修復貴,原因是要維護「新舊並行」期間的雙寫/路由層;但比 greenfield 便宜,因為 W5/GC3/contextPackets/falDispatcher/RAG 是整包搬遷而非重寫,且新地基的 schema/authz/ledger 是一次性投入、不用在舊 102 表污染的基礎上打補丁。

### 風險
- **Second-system 風險中**:因為有「新地基」這個乾淨畫布,容易被拉去順便解決北極星以外的問題——需要在階段計畫裡明確鎖範圍(對齊門,參照既有 Q3 對齊門規格思路)。
- **回歸風險中低**:被搬遷的零件是「已驗證正確」的(W5 有並發回歸測試、GC3 是獨立模組),移植時風險集中在「介面層要不要改」而非「邏輯要不要重寫」——只要移植時原樣保留介面簽名,回歸面小。
- **資料遷移風險中**:是漸進遷移而非一次性遷移,可以做「雙寫 + 影子驗證」降低風險,但比選項 B 多了「兩套 schema 期間如何保持一致」的協調成本。
- **並行期營運成本**:新舊系統並行期間,監控/告警/on-call 要覆蓋兩套系統,這是常被低估的隱性工時。

### 何時該選它
- 需 Bruce 提供:團隊規模(能否同時維護新舊兩地基並行);對「北極星要多快上線」與「舊債要多徹底清」兩者的相對優先序;是否已有 IA0 提到的「集中式授權中介」設計共識可以直接拍板,還是要重新設計討論。
- 適合「舊系統債已系統性到原地打補丁會反覆復發(本次稽核判斷 Y5/CC2/DI-01/B-27 一類屬此),但已驗證的核心零件(W5/GC3/contextPackets/falDispatcher/RAG)價值高到不該重寫」的中間情境——這正是本次稽核結論所描述的狀態,因此本研究判斷 **C 是三選項中與現狀證據最吻合的選項**,但這判斷仍需 Bruce 對下方分階段計畫的資源前提拍板才能執行。

### 對 prod 真實使用者/資料的敏感度
**中**——漸進遷移比一次性遷移安全,但仍需要「雙寫期間資料一致性」的工程紀律,若團隊沒有雙寫/影子驗證的經驗,實際風險會上修至接近選項 A。

## 5. 選項 C 的分階段計畫(strangler,新舊並行、逐模組切換)

範圍鎖定原則:每一階段只做該階段列出的項目,不順便碰下一階段的東西(對齊門,防 second-system 蔓延)。

### 階段 0(前置,不對外可見)
- 決定新地基的資料庫/授權技術選型(需 Bruce 提供:是否延用 Supabase/Postgres,或另擇平台)。
- 畫出新 schema 的 FK 關係圖,涵蓋現有 102 表中「北極星路徑實際會用到」的子集優先(不必一次補齊全部 102 表的 FK)。

### 階段一:地基 + authz + billing(最高優先,任何後續模組都依賴它)
- 新建 FK 齊全的 schema(對應 DI-01),優先只建北極星與計費會碰到的表,其餘表留在舊庫。
- 建 IA0 建議的「集中式物件授權中介」,取代 client 布林邊界的 IDOR 反模式(Y5/CC2)——這一步是整個 strangler 計畫裡對「系統性復發債」唯一的根治點,必須在階段一做,不能延後。
- 把 W5 的 `deductUserPoints`/`refundUserPoints`/`atomicClaimJobRefund` 原樣搬進新地基(介面簽名不變),疊加 IA0 建議的冪等 ledger + outbox 設計,同時解 B-27/B-31/B-32/B-22/X3 這串計費外圈失效(這些是「外圈沒接住核心原語」的問題,搬遷時一併把外圈補上,而不是只搬核心再重犯外圈的錯)。
- 搬 GC3 `secretCrypto`(125 行、零框架依賴,直接複製即可,幾乎零風險)。
- 產出:一個可獨立跑「使用者+授權+計費」的新地基,尚未接生成/UI。

### 階段二:移植生成派工
- 搬 `falDispatcher`、模型目錄、fal/replicate/suno 整合、`contextPackets` 單專案上下文子系統、RAG 管線。
- 這些模組在舊系統裡耦合度未知需逐一 Grep 確認(尤其是否深度依賴 8087 行 `agentToolExecutor.ts` 的內部狀態)——**若確認深度耦合，要先做「介面切割」再搬，不要把巨石一起搬過去**;若耦合淺(僅呼叫),可整包搬遷。
- 新地基此時應可跑「登入 + 授權 + 計費 + 生成」完整鏈路,但北極星 UI 尚未接上。

### 階段三:北極星主幹(可提前,視團隊資源而定)
- 把 `ProjectFlowGuide.tsx`(204 行)與五步引導所需的路由/狀態接到新地基。
- 因為 ProjectFlowGuide 體積小、耦合淺,實務上可以與階段二平行進行而非嚴格序列——但仍建議先確認階段一的 authz/billing 閘門已就位,否則北極星會重新繼承 Y5/CC2 的 IDOR 反模式。
- 此階段完成後,新系統應具備「登入→五步引導→生成→計費」完整垂直切片,可對一小部分流量(需 Bruce 決定切多少比例、哪些使用者)開放做影子驗證。

### 階段四:汰換舊殼
- 舊系統裡的 8087 行 `agentToolExecutor.ts`(178 個不可達工具)、三套並存記帳、shell 路由 shadow、北極星旗標 OFF 的殘留 UI——這些是「明確判定不移植、只汰換」的部分。
- 汰換順序:先關閉不可達工具與 dead code(低風險,無流量走它),再逐一比對三套並存記帳何者為新地基已取代的舊帳本並下線,最後移除 shadow 路由。
- 全部流量切到新地基後,舊 repo 的殼(不含已搬遷零件)可封存或刪除。

### 分階段小結
- 階段一、二是「必須先做」,順序不可換(authz/billing 是階段二生成模組的依賴)。
- 階段三可與階段二後段平行。
- 階段四必須等階段三驗證過一小部分流量後才開始,不能提前——否則就是在舊殼還在服務真實使用者時拆真實使用者依賴的東西。

## 6. 明確待 Bruce 拍板的變數清單

以下任一變數改變,都可能讓上述選項排序反轉,需 Bruce 提供才能鎖定最終建議:

1. **prod 目前真實使用者數/資料量級**——決定 A 是否可行、B/C 遷移窗口的緊急程度。
2. **團隊規模與能否同時維護新舊兩套系統**——決定 C 的並行期是否撐得住,以及 A 的「重新驗證全部正確性」是否有足夠人力。
3. **時程壓力(是否有硬性上線日期)**——A 最慢、C 次之、B 最快,但「最快」是建立在既有藍圖工時估算之上,若時程極緊,可能反而要壓縮 C 的階段一(先做 authz 再上線,不能跳過)。
4. **對「舊債徹底清除」vs「北極星盡快可見」的優先序**——若 Bruce 要盡快看到北極星能跑,C 的階段三可提前;若要求先徹底解決系統性債,階段一要做得更完整才能進階段二。
5. **是否已有 IA0 集中式授權中介的設計共識可直接拍板**,還是需要重新開會定案——這直接影響階段一的工時估算是否準確。
