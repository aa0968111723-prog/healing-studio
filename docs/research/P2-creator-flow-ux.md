## 0. 一句話定位

**不是設計一套新工具,是把 `ProjectFlowGuide.tsx` 這張「北極星五步嚮導」從 `/video` 座艙的一個抽屜裡放大成整條主線的骨架,幕內組裝與拼接輸出兩段補新畫面,其餘全部沿用座艙既有零件。** 本藍圖的每一張畫面設計都先問「座艙裡有沒有這塊」,答案是「有」就標注重用路徑,答案是「沒有」才畫新畫面(只有逐幕三軌編輯器、拼接預覽、輸出打包三張是淨新增 UI)。

## 1. 一條龍畫面地圖

下面把「建立專案 → 腳本 → 分鏡 → 逐幕組裝 → 拼接 → 輸出 → 打包」拆成 7 個畫面態,每態寫:**看到什麼 / 做什麼 / AI 在哪裡怎麼帶 / 防跑偏怎麼擋**。座標系統統一沿用座艙既有三欄(左 Story Spine / 中 Canvas / 右 Sidecar)+ 頂部 CreationFlowBar + 右下光球,不新開版面語言。

### 畫面 0 — 進站(尚無作用中專案)

```
┌ VideoCockpit(empty 態,已是既有程式碼,見 G1 §1.2)──────────────┐
│  🎬 尚未選擇專案                                                │
│  [ 建立新專案 ]   [ 選擇既有專案 ▾ ]                            │
│                                                                  │
│  光球(silent 態,右下呼吸球):輕點開啟 → 「先建立一個專案,       │
│  我會一步步帶你從腳本走到成片。」                                │
└──────────────────────────────────────────────────────────────────┘
```
- **看到**:既有 VideoCockpit empty 態(loading/error/empty-未選/empty-空白/success 五分支之一,`VideoCockpit.tsx:63-174`)。
- **做**:建立專案(輸入標題)或選既有專案下拉(`spine.projects`)。
- **AI 在哪**:光球 `silent` 態,不主動彈泡泡打斷——建立專案前創作者還沒有「專案上下文」可讀,對齊門(見 §4)天生放行,不用特別設計。
- **防跑偏**:此時無 `projectId`,一切照 M2 §6.2「沒有 active project 時直接放行」的既有設計原則,不需要對齊門介入。

- **看到**:`ProjectFlowGuide` 五步條(世界觀→劇本→分鏡→生成→成片),當前步高亮,`WorldLinkPicker` 內嵌選單。
- **做**:選一個既有世界連結,或跳過(此步非必經,`hint` 提示但不擋路)。
- **AI 在哪**:五步條本身就是「AI 讀專案狀態算出下一步該做什麼」的視覺化(`deriveProjectJourney` 純函式推導,見 §3.2);此階段光球泡泡可提示「要不要先連結世界觀,分鏡會更一致?」但按「稍後」也能繼續。

## 3. 關鍵畫面設計(四張)

### ① 專案儀表板(單一專案上下文一目了然)

**定位**:創作者打開專案的第一眼,要能秒懂「這個專案現在在哪一步、卡在哪、AI 建議做什麼」。

**資訊架構**(由上到下):
1. **專案身分列**:標題、emoji、狀態徽章(draft/in_progress/...)、專案切換下拉(座艙已有 `spine.projects` 切換器)。
2. **五步進度條**(重用 `ProjectFlowGuide` 的 steps 陣列,放大成儀表板主視覺而非側欄小條):世界觀/劇本/分鏡/生成/成片,每步打勾/未打勾/當前高亮,附一句話現況(`detail` 欄位既有文案可直接用)。
3. **世界觀摘要卡**:重用 `ActiveProjectContextPanel` 的 `SummaryRow`(世界觀/風格/最近素材/未完成任務/更新時間),把它從 `/create` 頁搬進座艙儀表板(或在座艙內新增同等摘要,資料源相同)。
4. **確認門總覽**:`countGate` 三態(就緒/待補/擋下)大數字,點擊 deep-link 到第一個問題鏡(既有 `StorySpineColumn` 邏輯搬到儀表板卡片尺度)。
5. **AI 建議區**(新):承接五步進度條的「下一步」文字,放大成一張「下一步建議卡」(見 §4.1),不是被動顯示,是可一鍵執行的主鈕。

**主要操作**:切換專案、點五步條任一步跳轉、點確認門數字 deep-link 修復、點「下一步建議卡」主鈕直接執行。

**AI 引導掛在哪**:儀表板本身就是「AI 讀單一專案上下文」的視覺化出口——`deriveProjectJourney`(§3.2 提及,規劃中的共用模組)算出的 `currentStep`/`nextAction` 直接餵這張卡,不需要另外呼叫 LLM。光球泡泡在儀表板頁面保持 `silent`/`hint` 態,不用 critical(除非有擋下的確認門)。

**防跑偏怎麼呈現**:五步進度條不可跳著點兩步以上完成(五問第 2 條的視覺對照——未完成的步驟前面步驟若也未完成,UI 上該步按鈕維持非當前態的樣式,引導創作者從當前步開始,而非放任跳步)。世界觀摘要卡的「未完成任務」清單即目標對照的雛形(M4 目標追蹤的產品化起點)。

### ② 逐幕組裝畫面(字卡+圖影+聲音三軌並列可編)

**定位**:把 G2 §3.1 指出的「`StoryboardTimelinePreview` 純顯示、無法逐項編輯」升級為真編輯器,是本藍圖**唯一的核心新建畫面**。

**資訊架構**:
1. **幕導覽列**(頂部):`◀ 上一幕 / 幕 S02 · 00:12~00:18 / 下一幕 ▶`,取代整段時間軸只能整體看的現況,聚焦單一幕編輯(呼應 ShotDetailCanvas 既有「聚焦單一鏡頭修復」的互動模式,幕級別的放大版)。
2. **字卡軌**(新,G2 §D4 指出型別目前 0 存在):文字輸入框(對應 `StoryboardFrame.captionText` 或場景層 `titleCardText`,依 M1 軌 D4 建議二選一)+ 樣式下拉(可選,不做通用字幕系統)。
3. **畫面軌(圖/影)**:直接沿用 `ShotDetailCanvas` 的大圖預覽+生成/核准/同 seed 重生 UI 骨架(M1 軌 D3 已指出可直接沿用),新增「kind=image/video」切換(依賴 M1 軌 C 的 kind=video adapter 補完)。
4. **聲音軌(配音/音樂/音效)**:清單式呈現該幕的 `audioClips[]`(kind=music|voiceover|sfx),沿用 `VoiceAmbientCanvas`/`MusicCanvas` 既有生成面板(座艙已有,完整),差別是結果要寫回**該幕**的 audioClips 而非目前散落呼叫(M1 軌 D3);每筆音軌可播放試聽、刪除、拖動 `startOffsetSec`(輕量數值輸入,非 DAW 級拖曳)、調 `volume`。
5. **底部**:「+ 新增音軌」按鈕(選 kind → 開對應生成面板)。

**主要操作**:改字卡文字、重生/替換畫面、增刪音軌、調時間偏移與音量、切換上一幕/下一幕。

**AI 引導掛在哪**:光球在此畫面的角色偏向「逐項核對」——例如某幕只有畫面軌沒有聲音軌時,光球 hint 態提示「這幕還沒有配音,要現在生成嗎?」;字卡留白時提示「要不要用這幕的對白草擬一句字卡?」。這些提示都是**建議**,不自動代填,创作者仍要按確認鈕(呼應座艙既有「光球只協助,不替你決策」的既定文案,`AmbientOrb.tsx:114`)。

**防跑偏怎麼呈現**:三軌的時間基準(`atSec`+ 各軌 `startOffsetSec`)全部相對同一幕的起點,不允許音軌偏移超出該幕的 `durationSec` 範圍(輸入即時校驗,而非事後才發現拼接錯位)——這對應 M1 §6-3「三者都以此排序,不各自維護一份順序邏輯」的設計要求。字卡/畫面/聲音三軌各自獨立可編,但**幕本身的順序**(哪一幕在前)不在此畫面調整,回到左欄 Story Spine 或 §3③ 拼接預覽處理,避免逐幕編輯器範圍蔓延成分鏡重排工具。

### ③ 拼接預覽畫面

**定位**:讓創作者在按「輸出」前,先看到「多幕串起來長什麼樣」,對齊 M1 軌 E「簡易拼接=順序串接+疊音軌+可選字卡疊圖,不要求轉場特效」的定義,不是專業剪輯台。

**資訊架構**:
1. **預覽播放器**:依 `atSec` 排序播放已核准幕的串接結果(初版可先是「逐幕縮圖走廊+點擊跳播單幕」,待 compose 服務上線後升級為「真的拼好的一支影片試看」)。
2. **時間軸色塊列**:每段幕依 `atSec`/`endSec` 定位的色塊(沿用 `StoryboardTimelinePreview` 既有時間尺畫法,G2 §3.1),點擊跳到該幕。
3. **未核准警示**:未核准的幕在時間軸上以警示樣式標出(沿用 `RoughCutCanvas` 既有 `PackGateSummary` 三態摘要:可打包/待核准/未生成),文案明講「未核准會被跳過」。
4. **底部動作**:「重新整理預覽」「回去核准」「進到輸出」。

**主要操作**:瀏覽拼接後的順序與內容、發現未核准的幕、跳轉回去核准、confirm 後前往輸出。

**AI 引導掛在哪**:此畫面是「AI 核對」而非「AI 生成」的最佳落點——光球扮演 M2 §3.3 提到的 `critic.review` 角色(工具目前不可達,見 §5),用一句話總結「3/5 幕已核准,S03 因未核准會被跳過,要現在去核准嗎?」,搭配兩按鈕(「去核准」/「先這樣拼接」)。

**防跑偏怎麼呈現**:「未核准鏡頭不打包」是既有 `RoughCutCanvas` 的鐵則(:76-77 `canPack` 判準),拼接預覽延續同一條規則,不新增例外——對齊門五問第 5 條(沒有繞過核准門)在此畫面是**視覺化**而非只在背景判斷,創作者親眼看到哪一幕會被跳過。

### ④ 輸出打包畫面

**定位**:一鍵拿到成片+一鍵拿到「成片+素材+腳本」的完整交付包,是北極星「一句話→成片」的終點。

**資訊架構**:
1. **成片播放器**(`outputUrl` 有值時):沿用 `CompletionCanvas` 既有 `VideoPlayer` 元件(播放+下載),`outputUrl` 由新建的 compose 服務(M1 軌 E)完成後回填。
2. **組合中佔位**(`outputUrl` 無值時):沿用既有 `AssemblingPlaceholder`(顯示 N/M 已生成 + 待後端徽章),但語意從「等 zip_export worker」進化為「等 compose 服務跑完」。
3. **打包鈕**:「打包全部(成片+素材+腳本).zip」——擴充既有「匯出素材包」邏輯(`CreationFlowBar.tsx:240-336`),新增「腳本文字」與「拼好的成片」兩個輸入來源,其餘 JSZip 邏輯不變。
4. **已核准分鏡縮圖走廊**:沿用既有 `ShotStrip`,作為交付前的最後視覺確認。

**主要操作**:下載成片單檔、打包完整交付包、(若還想調整)回頭跳回任一幕重編。

**AI 引導掛在哪**:此畫面是「AI 總結」的落點——五步條全打勾後,光球給一句總結+選項:「專案完成了。要打包交付,還是想再調整某一幕?」對應 M2 提到的 `orchestrator.getTeamStatus`(跨精靈進度回報,工具目前不可達)。即使 AI 工具層還沒接上,`deriveProjectJourney` 純函式本身(§3.2 已證明可行、不需要 LLM)已經能算出「全部完成」這件事,可以先用純前端判斷做這句總結,不必等 AI 工具鏈修好。

**防跑偏怎麼呈現**:打包完成不代表「專案結束不能改」——對齊門在終點之後放寬(不再攔「回頭改某一幕」的請求),因為北極星的「一步步建構」允許反覆修訂,不是單向流水線。

## 4. AI 引導的 UX(光球一步步帶你走)

### 4.1 下一步建議卡(常駐,貫穿全程)

**長相**(基於現有 `ProjectFlowGuide` 主鈕 + `AmbientOrb` 泡泡兩種既有元件合成的設計):

```
┌───────────────────────────────────────┐
│ 🔮  下一步建議                         │
│                                         │
│  你目前在「分鏡」步驟,還有 2 鏡待補角色 │
│  參考照才能生成。                       │
│                                         │
│  [ 去補角色參考照 ]      [ 稍後 ]       │
└───────────────────────────────────────┘
```
- 位置:延續光球 `hint` 態泡泡的既有版位(右下角,`AmbientOrb.tsx:60-89`)。
- 內容來源:`deriveProjectJourney(project)` 純函式(規劃中,§5 標為「共用重構」而非新邏輯)的 `currentStep`/`nextAction`/`detail` 三欄直接映射。
- 兩按鈕結構:CTA(執行建議動作,如 deep-link 到修復點或觸發 `spine.scheduleGeneration`)vs「稍後」(關閉泡泡,不做任何事,不重複打擾——沿用既有 `dismissBubble`)。
- **不跑偏之處**:此卡永遠只建議「當前步驟或下一步驟」的動作,不會建議「兩步之外」的事(對齊門五問第 2 條的正面呈現)。

### 4.2 對齊門澄清卡(跑偏時觸發,取代靜默執行或靜默失敗)

**觸發時機**:五問(同專案/同或下一階段/專案內已知實體/指向終點/沒繞過核准門,M2 §6.1)任一 fail。

**長相**(結構借用 `AmbientOrb` 泡泡的 CTA+稍後兩按鈕殼,文案改為澄清問句):

```
┌───────────────────────────────────────┐
│ 🔮  等一下,先確認一下                  │
│                                         │
│  這個角色「阿光」我在這個專案裡還沒     │
│  見過——是新角色,還是你想說「小明」？    │
│                                         │
│  [ 是新角色,建立它 ]   [ 我是說小明 ]   │
└───────────────────────────────────────┘
```
或(階段跳步情境):
```
┌───────────────────────────────────────┐
│ 🔮  等一下,先確認一下                  │
│                                         │
│  世界觀還沒連結,直接生成的話角色會少了  │
│  一致性參考。                           │
│                                         │
│  [ 先連結世界觀 ]     [ 照原計畫生成 ]  │
└───────────────────────────────────────┘
```

**設計原則**(對齊 M2 §6.4「創作者版 STOP-realign」):
1. **不執行、不報錯**——原本要直接跑的動作降級為這張卡,不是紅色錯誤,也不是靜默吞掉。
2. **只講最先 fail 的一條**,不是五條規則一次倒出來嚇人。
3. **兩個按鈕而非開放式追問**——一鍵「照你剛說的做」/ 一鍵「先完成目前這步」,把攔截轉成一次低成本確認,創作者不需要讀規則說明。
4. **確認後即成為新事實**——選了「是新角色」,對齊門下一輪就認得這個新角色,不會重複問。
5. **視覺上與「下一步建議卡」同殼不同色**(例如邊框從中性色變暖黃提醒),讓創作者一眼分辨「這是建議」還是「這是要我確認」,但兩者都遵守「兩按鈕、不強制」的互動語言,不引入第三種對話模式。

### 4.3 逐步引導的節奏設計(貫穿全程的行為準則)

- **一次只問一件事**:不論是下一步建議卡或對齊門澄清卡,同一時刻只出現一張卡,不堆疊多個泡泡(呼應 G1 §3.2-1 指出的「右下角浮動元件疊羅漢」問題——本藍圖的引導卡設計刻意收斂成單一入口,不新增第二個光球)。
- **可被忽略、不強制**:任何引導卡都有「稍後」/等價退出選項,創作者可以完全不理光球、靠左欄 Story Spine 與五步條自行導航——AI 引導是輔助軌,不是唯一路徑。
- **深度操作沿用既有「不繞過 LLM」模式**:對於「直接照建議做」這類明確動作,參考 `OrbGuidePanel.tsx` 既有「按鈕級直接 dispatch,不繞 LLM」的作法(G1 §1.7、M2 §3.2 表),不是每次都重新問一次 LLM 該做什麼,省成本也更可預期。

## 未查證/未涵蓋部分

- **compose 服務的實際輸出畫面**(拼接動畫進度條長什麼樣、失敗重試 UI)未設計細節——本文件只定義「拼接預覽」與「輸出」兩張畫面的靜態資訊架構,compose 任務執行中的即時進度呈現需待技術 spike(ffmpeg vs 委外 API,M1 §E4)結果出來後再定。
- **字卡欄位最終落在 `StoryboardFrame.captionText` 或場景層 `titleCardText`**——M1 軌 D4 標記「二選一,待創作者實測後決定」,本文件的逐幕組裝畫面（§3②）字卡軌設計對兩種選項皆相容,未預先裁定。
- **多專案並行時「下一步建議卡」與「對齊門」的行為**——M2 已明確聲明「僅涵蓋單一 active project」;若創作者同時開兩個專案分頁,建議卡/澄清卡該認哪個專案未在本文件涵蓋範圍。
- **語音入口(OrbVoiceButton)的引導體驗**——M2 §未涵蓋部分已排除,本文件同樣不涉及「用說的」引導這條線。
- **對齊門五問的實際判準門檻(例如「同或下一階段」容許跳幾步）**——本文件沿用 M2 §6.1 的文字定義,未做額外量化或反覆推敲邊界情境(例如「世界觀跳過直接寫劇本」算不算跑偏,§1 畫面 1 已假設「不算」,但這是本文件的設計判斷,非既有規格白紙黑字裁定,值得與 Bruce 對一次)。
- **儀表板(§3①)是否為全新路由頁面,或座艙內既有 `success` 態的擴充**——本文件描述其資訊架構,但「應該長在哪個 URL/是否取代 VideoCockpit 現有 success 態首屏」未裁定,留給後續 UI 落地時決定。
