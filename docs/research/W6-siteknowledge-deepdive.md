## 檔案角色(先讀後判)

`server/services/siteKnowledge.ts` 是純「知識/提示詞組裝」模組,不直接碰 DB、不直接呼叫 LLM、不做計費扣點。核心產出兩類:

1. **靜態知識字串常數**(約佔全檔 60%):`SITE_PAGES_KNOWLEDGE`(179行起)、`GENERATION_MODALITIES_KNOWLEDGE`(325行起)、`MODEL_RECOMMENDATION_KNOWLEDGE`(468行起)、`WORKFLOW_KNOWLEDGE`(577行起)、`STUDIO_CREATIVE_GUIDANCE`(647)、`IMAGE_STUDIO_CREATIVE_GUIDANCE`(724)、`PROMPT_LIBRARY_CREATIVE_GUIDANCE`(868)、`VIDEO_STUDIO_CREATIVE_GUIDANCE`(1111)。
2. **動態組裝函式**:`buildOrbSystemPrompt()`(1661行)、`buildDirectorSystemPrompt()`(2104行),把上述靜態知識 + 呼叫端傳入的 `OrbPromptExtras`(pageSnapshot / recentFeedback / assetLibrary / userIdentity 等)拼成最終系統提示詞。

**主要呼叫端**:`server/routers/ai.ts`(光球聊天 `ai.chat`,呼叫 `buildOrbSystemPrompt`)、`server/routers/director.ts`(導演 AI,呼叫 `buildDirectorSystemPrompt` + 直接內插 `GENERATION_MODALITIES_KNOWLEDGE` / `WORKFLOW_KNOWLEDGE`)。`buildOrbSystemPrompt` 的 `extras` 由 `ai.ts` 在 tRPC handler 內組裝,其中 `pageSnapshot`、`recentFeedback`、`context` 三個欄位**直接來自 client 的 mutation input**(zod schema 見 `server/routers/ai.ts:440-533`),其餘欄位(assetLibrary、userIdentity、specialistHints…)來自 `ctx.user.id` 範圍查詢的 DB 資料。

以下依「發現→影響→建議」、按嚴重度排序。

## 🔴 高:`buildOrbSystemPrompt` 的 `pageContext` 對 client 自由文字完全不設防,且繞過既有的注入防禦

**發現**

- `server/services/siteKnowledge.ts:1682-1684`:
  ```ts
  const contextNote = pageContext
    ? `\n\n【使用者目前在：${pageContext}】\n根據使用者所在頁面，提供貼心的相關建議。`
    : "";
  ```
  `pageContext` 是 `buildOrbSystemPrompt(personality, pageContext?, extras?)` 的第二個位置參數,被原封不動插進系統提示詞,且用「【使用者目前在：…】」這種**權威語氣**呈現給 LLM,緊接著指示模型「根據…提供…建議」——等於直接要求模型對這段文字採取行動。
- 回頭看呼叫端 `server/routers/ai.ts:440-443`:`context: z.string().max(10_000).optional()`(舊版純文字欄位,10,000 字上限,**無內容過濾**),以及 `ai.ts:1240-1248` 把 `input.context` 與 `worldContextBlock`、`persistedOrbMemorySummary` merge 成 `mergedPromptContext`,直接傳給 `buildOrbSystemPrompt` 當 `pageContext`(`ai.ts:1252-1254`)。
- 對照既有的注入防禦 `sanitizeOrbMessages`(`shared/orb-prompt-defense.ts`,專門攔截 `<|system|>`、`[system]:`、"ignore previous instructions" 等角色偽裝/越獄字串):它只套用在 `input.messages`(`ai.ts:1543-1548`),**而 `input.context` 從未經過 `sanitizeOrbMessages`**——`systemPrompt = buildOrbSystemPrompt(...)` 在 `ai.ts:1252` 執行,早於 `ai.ts:1539-1554` 才跑的 sanitize 流程,兩者是完全獨立的資料流。
- 更進一步,`buildOrbSystemPrompt` 內部用這串已被污染的 `pageContext` 做子字串比對來決定要不要塞入整段「深度代理指引」區塊(`siteKnowledge.ts:1717-1742`):
  ```ts
  const isStudioPage =
    extras?.pageSnapshot?.pageId === "studio" ||
    pageContext?.includes("/studio") ||
    pageContext?.includes("創作工作室") ||
    false;
  ```
  同樣邏輯用於 `isImageStudioPage` / `isVideoStudioPage` / `isPromptLibraryPage`。由於 `pageContext` 混入了使用者可控的 10,000 字自由文字,使用者可用「/video-studio」「創作工作室」等關鍵字讓不相關頁面的整段深度引導區塊(`STUDIO_CREATIVE_GUIDANCE` 等,見 `siteKnowledge.ts:2067-2070`)被灌進系統提示詞。

**影響**

- `context` 欄位可承載未經清洗的角色偽裝字串(`<|system|>`、`[system]:` 等 `orb-prompt-defense.ts` 原本要攔的模式),而它是以**比 chat message 更高信任框架**("使用者目前在…")直接注入系統提示詞,是比一般訊息注入更危險的旁路,現有防禦對它完全無效。
- 頁面偵測邏輯可被使用者自由文字操弄,導致「反焦慮協定」「跨頁面 Action 回退規則」等仰賴 `isStudioPage` 等旗標的行為判斷失真(例如觸發不對應頁面的深度指引/行為範本)。
- 因為光球的核心防線是「先說明再要求確認」(`【反焦慮協定】`,`siteKnowledge.ts:1998-2004`),真正的安全底線落在破壞性動作需要 `[CONFIRM:true]` 這層,故此問題目前較難直接兌現為「代使用者本人扣點/越權操作」,主要風險是**提示詞注入 / 越獄 / 誤導模型行為**,且是使用者對「自己的」助手做的操弄,尚未發現跨租戶擴散路徑(見下一條「owner」章節)。

**建議**

- 讓 `input.context` / `mergedPromptContext` 在送進 `buildOrbSystemPrompt` 前,一併跑過 `sanitizeOrbMessages`(或至少同等強度的角色標記剝除),而不是只套用在 `input.messages`。
- 用結構化欄位(`extras.pageSnapshot.pageId`)取代 `pageContext` 的子字串比對來決定 `isStudioPage` 等旗標,徹底移除 free-text 判斷頁面身份的路徑;`pageContext` 僅保留為「補充敘述」,不參與任何 boolean 判斷。
- 在系統提示詞裡明確加上分隔符與「以下內容為使用者自述,不代表系統事實」的免責語,而不是用「使用者目前在」這種等同系統宣告的措辭直接呈現使用者可控字串。

## 🟠 中:`learnHubOrbIndexCache` 的「靜態陣列」假設已被證偽,快取永不失效

**發現**

- `server/services/siteKnowledge.ts:76-80` 的註解聲稱:
  > `orbUnifiedSearch` calls this on every search keystroke… the underlying `docs` array in `learnHub.ts` is static at module load, so the bucketed result is stable for the lifetime of the process.
- `server/services/siteKnowledge.ts:81-107`:
  ```ts
  const learnHubOrbIndexCache = new Map<number, LearnDocSummaryForOrb[]>();
  export function getLearnHubOrbIndex(limit = 30): LearnDocSummaryForOrb[] {
    const cached = learnHubOrbIndexCache.get(limit);
    if (cached) return cached;
    ...
    learnHubOrbIndexCache.set(limit, result);
    return result;
  }
  ```
  沒有 TTL、沒有版本號比對,只有測試用的 `__resetLearnHubOrbIndexCacheForTests()`(114-116 行)。
- 但 `server/routers/learnHub.ts:50` 的 `docs` 其實是 **`let docs: LearnDoc[] = [...SEED_DOCS]`**,並非唯讀常數,且存在多處 runtime 寫入路徑:
  - `learnHub.ts:625-691` 的 `update`(adminProcedure mutation)直接執行 `docs[idx] = { ...docs[idx], ...updates, ... }`,可修改 `title` / `summary` / `featured` / `category` / `difficulty`。
  - `learnHub.ts:694+` 的 `delete` mutation 會從 `docs` 移除項目。
  - `learnHub.ts:209-216` 的 `upsertSeedDoc` 供 `syncAutoGeneratedLearnDocs()`(477 行,模組載入時執行一次)寫入/更新自動產生文件。
- `getLearnHubOrbIndex()` 有兩個呼叫端,都會共用同一份永久快取:`siteKnowledge.ts:123`(`buildLearnHubIndexKnowledge()`,餵給光球系統提示詞)與 `server/services/orbUnifiedSearch.ts:368`(`getLearnHubOrbIndex(60)`,註解自承「每次搜尋按鍵都呼叫」)。

**影響**

- 一旦流程首次呼叫過 `getLearnHubOrbIndex(30)` / `getLearnHubOrbIndex(60)`,之後任何管理員對學習文件的 `update`(改標題/摘要/精選狀態/分類)或 `delete`,都**不會反映到光球系統提示詞或站內搜尋**,直到整個 process 重啟。
- 具體後果:管理員下架或修正的文件,光球仍可能繼續用 `[ACTION:navigate:/learn?docId=<id>]` 推薦給使用者(可能導向已刪除或內容已變更的文件);新設為 `featured` 的文件不會出現在索引,直到重啟。
- 影響面同時涵蓋「AI 知識庫」與「使用者主動搜尋」兩個消費端,而非單一功能。

**建議**

- 為 `learnHubOrbIndexCache` 加上簡單的版本戳(例如 `learnHub.ts` 在每次 `docs` 被寫入時遞增一個 module-level `docsVersion`,`getLearnHubOrbIndex` 快取 key 改為 `${limit}:${docsVersion}`,或乾脆在 `learnHub.ts` 的 update/delete/upsertSeedDoc 路徑呼叫既有的 `__resetLearnHubOrbIndexCacheForTests()`(可考慮改名去掉 `ForTests` 後綴並在生產路徑呼叫)。
- 或直接拿掉這層快取——註解裡提到的效能動機(CPU profile 高)可用「快取上限固定 2 筆(30/60)+ 極輕量的分桶運算」重新評估是否真的需要跨請求持久化。

## 🟡 中:`recentFeedback.note` 未過長度上限、未過注入防禦,原樣拼進系統提示詞並要求模型「調整語氣」

**發現**

- `server/routers/ai.ts:476-492`:`recentFeedback` 的 zod schema 對陣列長度與 `note` 字串長度都**沒有 `.max()`**(`note: z.string().optional()`),只限制了 `status` 的 enum。
- `server/services/siteKnowledge.ts:1431-1443`:
  ```ts
  function serializeFeedbackBlock(list, now = Date.now()): string {
    if (!list || list.length === 0) return "";
    const recent = list.slice(-5);
    const lines = recent.map(ev => {
      const ageSec = ...;
      const note = ev.note ? `（${ev.note}）` : "";
      return `- ${ev.actionType}: ${ev.status}${note}｜${ageSec}s 前`;
    });
    return `【使用者最近對光球建議的反應（請參考並調整語氣）】\n${lines.join("\n")}`;
  }
  ```
  相較於同檔案 `serializeAssetLibraryBlock`(`1527-1531`)對 `promptUsed` 有 `.slice(0, 30)` 截斷,這裡的 `note` 完全沒有截斷或清洗,且該區塊標題明示「請參考並調整語氣」——等於直接要求 LLM 依這段使用者可控文字改變行為。
- `mergedFeedback = mergeFeedbackHistories(input.recentFeedback, dbEvents, 12)`(`ai.ts:1056-1060`)把 client 傳入的 `input.recentFeedback` 與 DB 內真實紀錄合併,前者未經任何伺服端驗證即進入這條管線。

**影響**

- 與上一條「高」風險同性質但影響更小(只截取最後 5 筆),仍是同一使用者對自己助手的注入面;主要風險是繞過語氣/行為引導、而非跨租戶資料外洩或計費繞過。
- 沒有長度上限也代表單次請求 payload 可以是任意大小(陣列筆數 + 每筆 note 長度都無界),雖然 `serializeFeedbackBlock` 只取最後 5 筆進提示詞,但**request body 解析本身**已經是 unbounded,屬於資源耗用面的次要疑慮。

**建議**

- 為 `recentFeedback` 陣列加 `.max(20)`、`note` 加 `.max(200)` 之類的上限;`serializeFeedbackBlock` 內對 `note` 補上與 `promptUsed` 一致的截斷。
- 評估是否也應該讓 `mergedFeedback` 或至少 client 端傳入的部分經過 `sanitizeOrbMessages` 等級的清洗,而非只信任 zod 的型別檢查。

## 🟢 低-中:2313 行單一巨檔,靜態知識與組裝邏輯混雜,契約漂移風險高但只有局部契約測試

**發現**

- 現有的 `server/services/__tests__/generationModalitiesKnowledgeContract.test.ts`(AIDV-631)只驗證 `GENERATION_MODALITIES_KNOWLEDGE` 這一個常數裡的**參數名**是否還存在於四個 compiler schema(`AudioCompilerInputSchema` 等)裡,**不驗證字串裡列出的具體 modelId 清單**(如 `nanoBanana2`、`seedreamV4`、`kling-t2v` 等數十個 modelId)是否仍與實際模型登錄檔(`imageStudio.ts`、`shared/orb-studio-actions.ts` 等)同步。若未來下架或改名某個 modelId,這份巨大的靜態表格可能在沒有任何測試失敗的情況下悄悄過期,光球會持續推薦已不存在的模型。
- `SITE_PAGES_KNOWLEDGE`(`siteKnowledge.ts:179-321`)本身有編號複製貼上錯誤:第 302 行「19. 專注流 (/focus-flow)」與第 308 行「19. AI 大腦設定 (/settings/ai-brain)」重複用了「19.」,而第 313 行直接跳到「20. 個人設定」——編號少算了一項,顯示這份文件維護時未同步檢查連號。

**影響**

- 屬於維護性/資料新鮮度風險,不是安全漏洞:模型下架/改名時,光球可能繼續建議已失效的 `modelId`,使用者體驗上出現「選了模型卻無法用」;編號錯誤是單純的文件品質瑕疵,不影響功能。

**建議**

- 比照 AIDV-631 的模式,替 modelId 清單也加一份「schema/registry 存在性」的輕量契約測試(哪怕只驗證『表格中出現的 modelId 都能在對應 registry 找到』這種存在性檢查)。
- 修正 `SITE_PAGES_KNOWLEDGE` 的編號(19/19/20/21 → 19/20/21/22)。
- 中長期可考慮把 8 個大字串常數拆到獨立的 `siteKnowledge/*.content.ts` 檔案,`siteKnowledge.ts` 只保留組裝函式,降低單檔行數與變更時的 diff noise。

## 📋 已查驗、確認無問題的項目(避免誤報)

- **owner/授權**:`buildOrbSystemPrompt` 的 `assetLibrary` 資料來自 `db.getDigitalAssetsByUser(ctx.user.id)`(`server/db.ts:1227-1236`,SQL `WHERE user_id = userId`),`recentFeedback` 的 DB 補充部分來自 `db.getRecentOrbFeedback(ctx.user.id, 10)`,`pageSnapshot.state.currentWorldFrameworkId` 對應的世界觀資料在注入前有做 `wb.userId === ctx.user.id` 擁有權比對(`server/routers/ai.ts:1193-1196`)——均確認為 user-scoped,未發現跨租戶洩漏路徑。
- **db.\* 查詢工具的「安全保證」宣稱屬實**:`buildOrbSystemPrompt` 系統提示詞裡對 `db.list_my_assets` 等工具宣稱「所有查詢自動限定為當前使用者」(`siteKnowledge.ts:1895-1899`)。追蹤到實際派送點 `server/services/agentToolExecutor.ts:900-917`(`dispatchDatabaseTool`),`userId` 是用 `{ ...args, userId: opts.userId }` 展開順序**強制覆寫**任何 LLM 可能夾帶的 `userId`,而 `opts.userId` 追溯到 `ai.ts:3035` 的 `ctx.user.id`(登入身份,非 client 可控)——此段提示詞宣稱與實作一致,非誇大宣稱。
- **計費/扣點**:本檔案不含任何點數計算、扣款或計費繞過邏輯(純知識/提示詞組裝),未發現直接的計費風險。唯一與成本相關的觀察是:`buildOrbSystemPrompt` 每次呼叫都會把 `SITE_PAGES_KNOWLEDGE`(約 6.1KB)+ `GENERATION_MODALITIES_KNOWLEDGE`(約 11.7KB)+ `MODEL_RECOMMENDATION_KNOWLEDGE`(約 5.3KB)+ `WORKFLOW_KNOWLEDGE`(約 3.0KB)+ 固定指令文字(`siteKnowledge.ts:1744-2097`,約 24.6KB)這五塊**逐字重新組裝**送進系統提示詞(合計約 50KB 靜態文字,每輪對話都相同),而全站程式碼庫內搜尋不到任何 `cache_control` / prompt-caching 相關字樣,顯示這塊高重複率的靜態內容目前並未使用 LLM prompt caching。這不是計費繞過,而是「重複、可快取的靜態 token 每輪都全額計費」的成本效率問題,值得評估是否導入 provider 端的 prompt caching。
- **buildDirectorSystemPrompt 無使用者可控輸入**:僅接受 `personality: "calm" | "creative" | "technical"` 一個受限列舉參數(`siteKnowledge.ts:2104-2106`),無 `extras`,不存在類似 `buildOrbSystemPrompt` 的注入面。

## 總結

本檔案本身不執行敏感操作(無 DB 寫入、無計費、無外部 API 呼叫),風險集中在「**餵給 LLM 的系統提示詞裡,有多少內容其實是 client 可自由控制的文字,且是否有跟現有注入防禦串接**」。最主要的一條(pageContext 直接注入且繞過 `sanitizeOrbMessages`)屬於高風險但影響範圍侷限在「使用者操弄自己的助手」,尚未發現能跨使用者擴散或造成計費/越權後果的路徑。次要問題集中在快取新鮮度(學習文件索引快取假設已被證偽)與 2313 行巨檔的維護性(死碼、編號錯誤、契約測試覆蓋不全)。
