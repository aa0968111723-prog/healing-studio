## 1. `/social` 一句話定位

`/social` ＝平台的**第二條創作線**：不是長片管線，而是「快速產一張對外圖文 → 鎖住品牌 → 一次匯出多平台尺寸 → 排程發佈」的**輕量線**。

它**不造新引擎**——把 `/video` 已建的 **cockpit 元件庫＋imageStudio（`generate.*`）＋showcase＋提示詞積木（`block_combos`）＋news/sense**，在 `/social` 這個**獨立 shell**裡**另實例化**一次。真正新增的語意只有三塊：**文字排版合成（`composeLayout`）＋多尺寸匯出（`exportSizes`）＋發佈通道（`PostingProvider`，mock→Postiz）**，外加兩個語意實體：**品牌身份（brand kit）＋社群貼文（post）**。

> 與 `/video` 的分界一句話：`/video` 鎖**角色**、核准**關鍵影格**、走世界觀/腳本/分鏡/i2v 長片管線；`/social` 鎖**品牌**、核准**單張對外圖文**、走輕量「brief→出圖→多尺寸→發佈」。要 `/video` 的素材時**只透過脊椎讀 `digital_asset_library`，不開 `/video` UI**。

1. **不自造色**：任何顏色都來自上表語意 token；需要新語意色 → 回報 `00_設計系統`（走 §13 版本進位），不在 `/social` 私設。

## 5. 保留原系統聲明（strangler-fig，加法不破壞）

實作 `/social` **不得**修改 `/video`、`/learn`、`/settings` 任何頁面，也不得改 `00_設計系統`。具體界線：

- **新增不刪改**：新增 `SocialShell.tsx`、`components/social/*`、`server/routers/social.ts`、（Tier-1 時）`brand_kits`/`social_posts` 兩張小表。既有 34 router、82 表、54 路由**一個都不動**。
- **feature-flag 包覆**：`SocialShell` 掛 feature flag，可隨時下架不影響 `/video`。新表純加法、可關。
- **脊椎單一實例**：`ProjectsContext`(active-project)、`PersonalSettingsContext`、`ThemeContext`、`BackgroundTasksContext`、`AIStateContext` 等**只在脊椎層一份**，`/social` 消費不複製（程式碼校正 `03` §3.2 已點名這些必須留脊椎）。
- **無孤兒**：每張產物 `linkAssetToProject` 回寫 `creative_projects` timeline；主鍵永遠是 `creative_projects`。
- **mock=real 一致**：所有狀態（核准/鎖定/成本/發佈）在 P2 mock 下的判定，切真實後**原樣搬移、判定不翻盤**。

## 6. 資料落地兩條路徑（與架構一致，現況 MySQL）

> ⚠ **schema 事實**（`03` §1）：drizzle 現況是 **MySQL（`mysqlTable`）**，非 PG。設計文件提到 Tier-1 新表「建在 PG、用 `jsonb/pgEnum/timestamptz`」是 **P3 之後目標**。實作 UI 時不依賴 PG 型別；後端落表時依當下 P3 進度決定 MySQL JSON 還是 PG jsonb。

| | Tier-0 · 零新表（先上 MVP） | Tier-1 · `brand_kits`/`social_posts` 小表（長期經營時升） |
|---|---|---|
| 品牌身份 | 一筆 `block_combos`（payload JSON 塞 logo/色/字/voice）＋`kind:'brand'` | 專屬 `brand_kits`（結構化欄位、可查詢/驗證） |
| 鎖定機制 | `consistency_vault` 一筆（`entityType:'brand'`，經 `vault.update` payload 表達鎖態） | `brand_kits.lockState`（語意同 vault，亦可雙寫 vault） |
| 貼文 | 產物資產 + 文案存既有表 + `project_notes_calendar` 排程 | `social_posts`（文案＋多資產＋多平台＋排程＋發佈結果聚合） |

UI 規格**對兩條路徑都成立**：畫面與狀態不變，差別只在底層 procedure（見 `08` 對照表）。建議**先 Tier-0 出 MVP**，品牌功能確定長期經營再升 Tier-1。
