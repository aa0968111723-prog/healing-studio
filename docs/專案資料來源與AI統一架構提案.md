# 專案、資料來源與 AI 統一架構提案

> 狀態：提案
>
> 目的：降低使用者在「專案、資料庫、Google 雲端、Notion、API、AI 助手、代理、生成與工作流」之間的理解與操作成本，將既有能力整合成一條以專案為中心的創作流程。

## 一、問題定義

目前各項功能本身有價值，但在使用者介面中被呈現為多個平行系統：

- 專案
- 資料庫
- 整合連接
- Google 雲端
- Notion
- 外部 API
- AI 助手
- AI 代理
- 生成
- 工作流
- 模型與 MCP

一般使用者因此難以判斷：

1. 應該先連接服務、建立資料庫，還是進入專案。
2. 檔案匯入後，AI 是否已經能讀取。
3. AI 助手、代理、生成與工作流有何不同。
4. 個人、專案、組別與團隊資料應該放在哪裡。
5. 完成目前工作後的下一步是什麼。

核心問題不是功能太多，而是底層技術名稱直接成為使用者必須理解的產品概念。

## 二、產品定位

產品統一定位為：

> **以專案為中心的 AI 創作工作空間。**

所有功能依下列模型重新歸位：

- **工作空間**：決定使用者目前位於個人、組別或團隊情境。
- **專案**：承載目標、資料、創作、任務、審核與交付。
- **資料來源**：提供 AI 與團隊可引用的文件和結構化資料。
- **AI 創作助手**：使用者唯一主要 AI 入口。
- **生成**：AI 助手可呼叫的內容產生工具。
- **製作範本**：預先定義好的固定工作流。
- **AI 執行計畫**：AI 依目標動態產生並在核准後執行的代理計畫。
- **權限**：控制資料與操作對個人、專案成員、組別或團隊的可見範圍。

使用者的主要流程應收斂為：

```text
進入專案
→ 加入資料
→ 告訴 AI 想完成什麼
→ 確認執行方案
→ 查看成果與下一步
```

## 三、資訊架構

### 3.1 全站主導覽

主導覽只保留五個主要入口：

```text
首頁
專案
知識與資料
任務
團隊
```

個人選單收納低頻與管理型入口：

```text
連接的資料來源
通知設定
帳號設定
進階 AI 設定
系統管理
```

MCP、模型目錄、API 金鑰與供應商設定不應成為一般使用者的第一層主入口。

### 3.2 首頁

首頁回答三個問題：

1. 我正在進行什麼。
2. 哪些事情需要我處理。
3. AI 建議我接下來做什麼。

建議區塊：

- 進行中的專案
- 我的任務
- 等待確認或審核
- 最近活動
- AI 下一步建議

### 3.3 專案工作區

每個專案收斂成四個主要區域：

```text
專案總覽
資料與企劃
創作
審核與交付
```

詳細內容：

```text
專案總覽
├── 目標與摘要
├── 目前進度
├── 下一步
├── 成員與負責人
└── 最近活動

資料與企劃
├── 世界觀與企劃
├── 已加入文件
├── 專案資料表
├── 角色與場景設定
└── 資料來源與同步狀態

創作
├── 腳本
├── 分鏡
├── 生成內容
├── 素材
└── 製作範本

審核與交付
├── 待審內容
├── 修改紀錄
├── 版本與時間軸
└── 匯出與交付
```

AI 創作助手應固定在專案右側抽屜或可隨時開啟的全域面板，不再只是頁面中的一張功能卡。

## 四、資料來源整合

### 4.1 統一名稱

原本分散的整合能力統一稱為：

> **連接的資料來源**

支援來源：

```text
我的裝置
Google 雲端
Notion
網頁網址
外部 API
既有文件與資料表
```

Google、Notion 與 API 是資料來源，不是獨立的創作功能。

### 4.2 專案內統一入口

專案內新增主要動作：

```text
加入資料
```

開啟後提供：

```text
上傳檔案
從 Google 雲端選擇
從 Notion 選擇
貼上網址
連接外部 API
選擇既有資料
```

使用者不應被要求先離開專案、前往整合頁完成設定，再回資料庫頁匯入。

若來源尚未連接，系統應在同一流程中引導授權，完成後回到原本的專案選取流程。

### 4.3 匯入完成後的必要狀態

每份資料應顯示：

```text
上傳中
解析中
AI 可讀
需要 OCR
解析失敗
同步中
同步失敗
```

匯入完成不能只顯示「成功」，還要立即提供：

- AI 是否可讀。
- 已加入哪個專案。
- 可讀字數或資料列數。
- 摘要與主要內容。
- 缺漏、風險與建議。
- 可轉成的下一步。

建議動作：

```text
深入分析
轉成任務
加入專案摘要
建立資料表
產生分鏡
建立 AI 執行計畫
```

## 五、知識與資料

### 5.1 使用者名稱調整

將一般介面的「資料庫」改為：

> **知識與資料**

內部分為：

```text
文件
資料表
連接來源
AI 使用範圍
```

底層資料表與資料庫模型可以保留，不要求在第一階段重寫資料結構。

### 5.2 資料範圍的自然語言

不要先要求一般使用者理解 personal、group、team、global。

建立資料時改問：

> 這份資料要給誰使用？

選項：

```text
只有我
這個專案的成員
我的組別
整個團隊
```

在專案內建立或匯入資料時，預設為「這個專案的成員」。

全站或管理員範圍保留在進階權限中。

### 5.3 AI 權限

使用者介面統一使用「AI 使用權限」：

```text
AI 不可使用
AI 可以閱讀
AI 可以閱讀與更新
```

所有寫入仍必須受使用者身分、專案權限、範圍權限及必要核准控制。

## 六、AI 系統整合

### 6.1 使用者只看到一個 AI

所有主要介面統一稱為：

> **AI 創作助手**

AI 創作助手提供四類能力：

```text
問：回答、搜尋、分析與比較
創作：腳本、分鏡、圖片、影片、旁白與文字
規劃：拆解目標、估算步驟與成本
執行：核准後自動完成多個步驟
```

使用者不需先判斷應使用助手、代理、生成或工作流。

### 6.2 底層能力對應

| 使用者意圖 | 系統能力 |
|---|---|
| 分析這份企劃 | 文件讀取與問答 |
| 產生一張宣傳圖 | 生成工具 |
| 將腳本拆成八鏡 | AI 動作 |
| 幫我完成三鏡並送審 | AI 執行計畫 |
| 每鏡生成圖片與旁白 | 製作範本或執行計畫 |
| 查詢 Notion 活動資料 | 資料來源檢索 |

### 6.3 生成

「生成」定位為創作工具，不是獨立產品。

一般使用者先選內容種類與品質：

```text
內容：圖片／影片／旁白／音樂／文字
品質：快速／平衡／精緻
```

模型名稱與供應商放入進階設定。

### 6.4 製作範本

將 Workflow 對外名稱調整為：

> **製作範本** 或 **自動流程**

範例：

- 腳本轉分鏡
- 分鏡轉圖片
- 圖片轉影片
- 訪談轉故事腳本
- 文章轉社群貼文
- 活動企劃整理

### 6.5 AI 執行計畫

將 Agent 對外名稱調整為：

> **AI 執行計畫**

使用者只在核准時需要理解：

- AI 準備執行哪些步驟。
- 哪些步驟會修改資料。
- 哪些步驟需要點數或外部服務。
- 預估成本。
- 是否需要組長核准。

範例：

```text
AI 已規劃以下執行方案

1. 讀取活動企劃
2. 找出資訊缺漏
3. 建立工作分工表
4. 建立三項任務
5. 將摘要寫入專案筆記

預估花費：0 點
[核准執行]
```

## 七、個人與團隊整合

### 7.1 工作空間概念

個人與團隊不建立兩套產品，而是使用同一套功能搭配不同工作空間與權限。

```text
工作空間
├── 我的空間
├── 團隊 A
│   ├── 組別 1
│   └── 組別 2
└── 團隊 B
```

切換工作空間時，以下內容同步切換：

- 首頁
- 專案
- 任務
- 知識與資料
- AI 上下文
- 審核與通知

### 7.2 預設規則

- 個人空間：只有本人可見。
- 專案內資料：預設專案成員可見。
- 組別資料：組別共用，組長管理。
- 團隊資料：團隊共用，管理員管理。
- 外部連線憑證：預設綁定個人，不直接共享秘密。
- 團隊共用連線：必須由管理員建立，並以受控連線身分使用。

## 九、分階段實作

本提案不得以單一大型 Runtime PR 完成。建議拆成以下階段。

### Phase 1：名稱與導覽收斂

目標：不改底層行為，先降低認知成本。

- 將「資料庫」主要文案改為「知識與資料」。
- 將「整合連接」改為「連接的資料來源」。
- 將「AI 代理」主要文案改為「AI 執行計畫」。
- 將「工作流」主要文案改為「製作範本」。
- 將 AI 入口統一稱為「AI 創作助手」。
- 將 MCP、模型與 API 設定移入進階入口。

驗收：

- 一般使用者不需要理解 Agent、Workflow、MCP 才能開始工作。
- 既有 URL 與後端 API 保持相容。
- 主要功能仍可透過原深連結進入。

### Phase 2：專案內「加入資料」

目標：把上傳、Google、Notion、網址、API 與既有資料收斂成同一流程。

- 新增專案內加入資料面板。
- 支援未連線時就地授權並返回原流程。
- 加入資料後自動綁定專案。
- 顯示解析與 AI 可讀狀態。

驗收：

- 使用者不必離開專案即可完成資料加入。
- 每份資料能追溯來源與專案。
- 權限預設不會擴大到其他組別或團隊。

### Phase 3：匯入後 AI 分析

目標：讓匯入成功直接產生可行動的結果。

- 匯入完成後執行或提供 AI 分析。
- 顯示摘要、缺漏、風險、證據與下一步。
- 支援轉成任務、摘要、資料表、分鏡或執行計畫。

驗收：

- AI 建議必須能指出來源文件或資料列。
- 解析失敗時提供可操作的修復說明。
- 掃描 PDF 明確提示 OCR 狀態。

### Phase 4：AI 單一入口

目標：由 AI 創作助手自動判斷使用問答、生成、製作範本或執行計畫。

- 專案內固定 AI 面板。
- Context 自動帶入工作空間、專案、目前頁面與選取內容。
- 使用者不必先選擇代理或工作流。
- 寫入與付費動作保留明確核准。

驗收：

- 同一個 AI 對話可完成查資料、分析、創作與提出執行計畫。
- 核准前顯示步驟、影響範圍及成本。
- 權限與點數守門不因入口整合而分岔。

### Phase 5：統一 Tool Registry

目標：讓網站助手、執行計畫、製作範本與 MCP 共用同一批工具定義。

每個工具至少描述：

- 名稱與用途
- 輸入與輸出 Schema
- 讀取或寫入
- 適用範圍
- 核准需求
- 成本類型
- 冪等與重試策略

第一批工具：

```text
project.read
project.update
knowledge.search
file.read
file.analyze
scene.create
scene.update
asset.generate
database.query
database.write
note.create
task.create
schedule.create
approval.submit
export.create
```

驗收：

- MCP 與網站內建 AI 不再維護語意不同的重複工具。
- 所有工具通過同一套 ACL、審計與成本政策。

### Phase 6：事件與長期記憶

目標：建立真正可延續的專案代理上下文。

事件示例：

```text
file.uploaded
file.parsed
project.updated
scene.updated
generation.completed
generation.failed
approval.rejected
approval.approved
task.overdue
```

記憶範圍：

- 使用者偏好
- 專案決策
- 失敗與退回原因
- 已採用版本
- 團隊規則
- 目前阻塞與下一步

驗收：

- AI 能說明建議依據的事件與決策。
- 記憶具有工作空間和專案隔離。
- 使用者可查看、修正或刪除可持久化記憶。

## 十、非目標

本提案第一階段不處理：

- 一次性重寫所有資料表。
- 一次性重寫所有代理執行器。
- 移除既有 API 或舊 URL。
- 自動授權 AI 寫入所有資料。
- 取消人工核准與點數守門。
- 在未完成權限與事件模型前實作完全自主代理。

## 十一、相容與遷移原則

- 優先調整呈現層與入口，不改既有核心 ID。
- 舊路由保留並導向新資訊架構。
- 舊文案與欄位名稱先以 alias 相容。
- 每個階段可獨立部署與回滾。
- 重大權限變更必須附跨範圍負向測試。
- 生成、工作流與代理仍沿用既有點數與核准守門。

## 十二、測量指標

重整成效以使用者行為衡量：

- 新使用者完成第一次「加入資料並詢問 AI」的成功率。
- 從加入資料到取得 AI 建議的平均操作步數。
- 匯入完成後仍不知道下一步的回饋數量。
- 使用者誤解 AI 助手、代理與工作流的支援問題數。
- 專案內完成生成、送審與交付的成功率。
- 未使用或未被專案引用的外部連線比例。
- AI 建議轉成任務或執行計畫的比例。

## 十三、完成定義

當以下條件完成，可視為本次產品架構整合達標：

- [ ] 一般使用者只需理解工作空間、專案、資料來源與 AI 創作助手。
- [ ] 專案內可直接加入 Google、Notion、API、網址與本機檔案。
- [ ] 每份資料都有解析、AI 可讀及同步狀態。
- [ ] 匯入後能直接取得有來源依據的 AI 建議。
- [ ] 生成、製作範本與執行計畫由同一 AI 入口調度。
- [ ] 個人、專案、組別與團隊的資料範圍有自然語言說明及安全預設。
- [ ] 網站 AI、MCP 與背景執行共用核心工具與權限政策。
- [ ] 專案首頁能明確顯示進度、阻塞與下一步。
